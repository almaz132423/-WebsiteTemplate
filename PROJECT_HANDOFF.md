# Передача контекста проекта — Создание сайтов под малый бизнес

Обновлено: 2026-10-23

Этот документ — точка передачи контекста между чатами. Перед началом работы в новом чате прочитать его и свериться с актуальным состоянием файлов в репозитории. Основной код и история изменений находятся в GitHub.

## 1. Назначение проекта

Создаётся универсальный шаблон статического сайта для малого бизнеса. В дальнейшем шаблон будет адаптироваться в отдельных чатах под конкретные компании. Не считать этот чат постоянным рабочим местом: возвращаться к нему только при необходимости восстановить исходный контекст.

Репозиторий: https://github.com/almaz132423/-WebsiteTemplate
Основная ветка: `main`.

## 2. Обязательные принципы из ТЗ

- Основной стек: HTML5, CSS3, обычный JavaScript; не внедрять React без отдельного обоснования и согласования.
- Сайт статический, без обязательного backend; сохранять возможность размещения на статическом хостинге и работу в подпапке.
- Данные компании отделены от интерфейса и хранятся в `config/business.json`.
- Основной сценарий сайта — сформировать заявку через форму, дать пользователю просмотреть/отредактировать/скопировать сообщение и перейти в настроенный мессенджер.
- Нельзя обещать автоматическую отправку сообщения или подтверждать запись без ответа компании. Дата/время — пожелания клиента, а не подтверждённые свободные слоты.
- `admin.html` — локальный редактор конфигурации с просмотром/добавлением/изменением/удалением услуг, редактированием основных данных, импортом и экспортом JSON. Сам по себе редактор не записывает изменения в репозиторий и не обновляет опубликованный сайт: после экспорта нужно заменить `config/business.json` в проекте.
- Не выдумывать данные компании, адреса, отзывы, цены, лицензии, достижения, фотографии или контакты. Неизвестное явно помечать как требующее уточнения.
- При адаптации сначала изучить проект, архитектуру, риски и план; затем выполнять работу небольшими согласуемыми этапами.
- Проверять адаптивность, доступность, семантику, SEO, валидацию формы, ссылки, относительные пути и поддержку `prefers-reduced-motion`. Не заявлять о проверках, которые фактически не выполнялись.
- В `README.md` содержится адаптационный промпт с 14 пунктами для работы под конкретный бизнес.

## 3. Основные файлы в репозитории

- `index.html` — главная страница сайта.
- `config/business.json` — конфигурация бизнеса, услуг, контактов, мессенджеров и полей заявки.
- `css/style.css` — основные стили сайта.
- `js/main.js` — поведение сайта, форма заявки и сценарий перехода к мессенджерам.
- `admin.html` — локальный редактор конфигурации.
- `css/admin.css` — стили редактора и экрана авторизации.
- `js/admin.js` — редактор JSON и локальная авторизация.
- `README.md` — описание проекта, инструкция использования/публикации, адаптационный промпт и ограничения.
- `PROJECT_HANDOFF.md` — этот документ, передача контекста между чатами.

Все файлы следует читать из текущей ветки репозитория перед существенными изменениями: состояние кода со временем может измениться.

### Локальная авторизация редактора
В коммите от 2026-10-23 добавлен экран первого создания пароля и последующего входа в `admin.html`:
- пароль длиной минимум 8 символов;
- в Local Storage хранится соль и SHA-256-хеш, а не сам пароль;
- статус входа сохраняется в Session Storage текущей вкладки;
- добавлена кнопка выхода;
- добавлены стили и описание в README.

Важное ограничение: это только базовый локальный барьер, а не полноценная защита. Статический код можно обойти через инструменты разработчика; нельзя использовать эту авторизацию для защиты чувствительных данных. Для реальной защищённой панели нужна серверная авторизация. Если нужно сбросить пароль, удалить ключ `businessTemplate.adminCredential.v1` из Local Storage для этого сайта и перезагрузить страницу. Для Web Crypto требуется HTTPS или localhost.

### Хостинг и заявки
Рассмотрены варианты бесплатного статического хостинга:
- Cloudflare Pages — основной кандидат для публичного статического сайта;
- Netlify — альтернатива, особенно если решим подключать обработку форм;
- GitHub Pages — годится для демонстраций, но перед коммерческим использованием нужно учитывать условия сервиса.

Сам хостинг статических файлов не создаёт хранилище заявок. Текущий сценарий передаёт подготовленное сообщение через мессенджер и не сохраняет заявки централизованно. Обсуждались три направления на будущее:
1. оставить ручную отправку в WhatsApp/Telegram/MAX;
2. подключить внешний сервис обработки формы с уведомлением по email;
3. сделать серверный обработчик и защищённый список заявок (например, Pages Functions плюс хранилище).

Решение о реализации одного из способов приёма заявок ещё не принято. Не добавлять backend/хранилище без согласования конкретного сценария.

## 7. Правила дальнейшей работы в отдельных чатах

Для каждого нового бизнеса использовать отдельный чат и конкретный бриф компании. В начале работы:
1. Прочитать этот handoff и текущие `README.md`, `config/business.json`, `index.html`, `js/main.js` и CSS.
2. Уточнить подтверждённые данные бизнеса и отметить отсутствующие сведения.
3. Предложить структуру/визуальную концепцию и план изменений; не переписывать проект целиком без необходимости.
4. В первую очередь адаптировать конфигурацию и контент; универсальную логику менять только по технической необходимости.
5. Сохранять все изменения в соответствующем репозитории только после согласованного объёма работ.
6. После этапа перечислять изменённые файлы, коммиты, реальные проверки и непроверенные пункты.
7. Не переносить в шаблон данные одного бизнеса в качестве фактов для другого клиента.

Если новый чат не имеет доступа к файлам проекта или GitHub, использовать ссылку на репозиторий выше и этот файл как точку входа. Не утверждать, что контекст автоматически сохранён в памяти ChatGPT: надёжный источник передачи — этот документ и актуальный репозиторий.
